# DeepSWE v1.1 × Codex（Harbor）：auto router 实验报告

> 表格与数字由 `experiments/deepswe-harbor/report_zh.py` 从 `results/report/report-data.json` 生成（第 6 节原样收录，未重新计算）；摘要和第 1–5 节是据此写成的正文。只记录任务 id 与汇总数，不含数据集文本。统计预注册见 `docs/tasks/11-05-deepswe-harbor-eval/design.md` §7。

## 摘要

问题：在 DeepSWE v1.1 的 112 个任务上（Codex CLI，effort high，Harbor 判分），router 的 `auto` + 评估器（B 组）与始终固定 Sol（A，standard）、Luna（F，fast）、Astra（C，frontier）相比，解决率和成本如何；“auto + 评估器的性价比最好”是否成立。每组每任务 5 次运行，共 2,240 次计分运行。

1. **相对 Sol，“auto + 评估器性价比最好”不成立。** B − A = −2.1 pp（95% CI [−5.4, 0.9]），10 pp 非劣性已显示；但成本是 Sol 的 4.06 倍（[3.61, 4.50]）。预注册的“B ≥ A 且更便宜”不成立，判定是“不劣于 A，但成本更高”。每解决一个任务：B $4.04，A $0.97。
2. **相对 Astra，成立。** B − C = −2.0 pp（[−4.9, 1.0]），非劣性已显示，成本 ×0.66（[0.59, 0.73]）：预注册的“B ≥ C 且更便宜”成立（盲设计集；用全部运行时判定相同）。如果原本会一直用 Astra，auto + 评估器省约三分之一，解决率差 −2.0 pp（[−4.9, 1.0]），10 pp 非劣性已显示。
3. **相对 Luna，B 解决得多得多，也贵得多。** B − F = +15.0 pp（[7.5, 22.6]），成本 ×21.98。Luna 本身：F − A = −17.1 pp（[−24.2, −10.2]，CI 整体在 0 以下），成本 ×0.18。
4. **原因：在这些任务上未检出 Astra 比 Sol 多解决任务（C − A = −0.2 pp，[−3.1, 2.7]）**，而成本是 ×6.11。线上评估器把 B 的 326/560 次运行（58%）送到 Astra（离线 tier pass 送去 frontier 的运行约 62%；按多数归为 frontier 层的任务是 72/112），这些运行付了 Astra 的价钱，却没有检出更高的解决率；B 的成本因此落在 Sol 与 Astra 之间（×4.06 / ×6.11）。
5. **未检出评估器的选择能力（+0.4 pp，[−5.3, 6.2]，区间宽）。** 选择能力 = (C − A | frontier) − (C − A | standard)：被判为 frontier 的任务上，未检出 Astra 相对 Sol 有更大的优势。平均而言未检出 Astra 多解决任务，留出版理想路由也几乎不选 Astra（3%），所以“送去 frontier”的判断在这里只增加成本。
6. **未检出 router 本身引入的问题。** 0 次 router 造成的失败、0 次 failover、0 次会话中换模型；每次 B 运行与服务它的模型的固定组相比，未检出差异（事后分析，见第 4 节）；评估器每次运行咨询 1 次，延迟中位数 1,231 ms，总花费 $0.40（B 臂的 0.024%）。四组都没有检出运行期间的漂移（S7b 的 CI 都包含 0）。
7. **花费（分析内的运行，proxy 账本）**：A $402.45，B $1,633.14（含评估器），F $73.85，C $2,454.06。实验总花费约 $4,657（含 pilot、重跑与 runner 时间；预算 $8,000，见第 1 节）。

## 1. 实验设置

- **任务**：`datacurve-ai/deep-swe` v1.1（Apache-2.0），固定提交；113 个任务中 1 个（prometheus-transactional-reload-status）未通过 oracle 检查而按预注册规则剔除，剩 112 个（113 个任务来自 91 个仓库、5 种语言）。
- **代理与判分**：Harbor 0.25.0 内置的 `codex` 代理，Codex CLI 0.166.0（固定版本与 sha256），reasoning effort high，`model = auto`；任务自己的超时（3 h）、CPU 与内存。判分由 Harbor 的独立 verifier 容器完成（离线），每次尝试再由预注册的分类器决定计分、重跑或排除（design §7.4）。
- **隔离**：agent 容器只能经宿主机代理访问 router（仅一个端口），verifier 容器没有网络；网关令牌只在代理里，从不进入容器。
- **组**：A 固定 Sol（`pin=Sol`）、F 固定 Luna、C 固定 Astra、B `auto` + 评估器（已部署的 router 配置）。四组走同一 router 路径，组别只体现在代理为该运行设置的 router hint 上。
- **运行**：每组每任务 5 次（A/B 的 rep 1–5；C/F 的 rep 1–3 与中期查看之后加入的 rep 4–5，见下方披露），四组在每个 pass 里按块交错运行；4 台 runner 按任务分片；共 2,240 次计分运行，重跑 5 次（verifier_infra 4、harness 1），没有排除。
- **总花费**：Bedrock $4,597.07（全部尝试，含 pilot；不含 pilot 为 $4,567.71，比四组分析内运行的 Bedrock 之和多约 $4.60：被重跑替换掉的首轮尝试 $6.90，减去逐调用计价与 proxy 累计之间 $2.30（0.05%）的口径差），runner 约 $56（4 × r7i.2xlarge + 250 GB，约 $2.69/h，11-05 14:37 至 11-06 约 11:30），评估器 $0.40；合计约 $4,657，预算 $8,000。
- **统计**：任务为单位、各次运行等权的 `paired_mean_diff`（成对 bootstrap CI、符号翻转 p），非劣性界限 10 pp；成本为 ΣY/ΣX（按任务平均成本）。判定规则预先登记：不说“等价”，非劣性“未显示”不等于“更差”。

> **中期查看披露（design §7.5.2、§11）**：决定给 C 和 F 加 rep 4–5 之前，main + rep2 上四个臂的中期解决率（以及每次运行的平均成本）已被计算并展示给用户。加运行的规则（每臂每任务 5 次）没有引用这些结果，但无法证明没有它们决定会相同，所以 C/F 的 rep 4–5 视为“在中期查看之后加入的运行”。P1/P2 不受影响（A、B 没有这样的运行）；S1/S2 的判定基于盲设计集（A/B rep 1–5，C/F rep 1–3），含这些运行的同一比较并列显示，两者判定不同时保留盲设计集的判定；S3–S5 使用全部运行，用到这些运行时加标注。本报告中这样的运行：C 224 次（计分 224），F 224 次（计分 224）。

## 2. 解读：为什么 auto + 评估器在这里不划算

- **决定性的事实是：未检出 C 与 A 的差异。** 112 个任务、每组 5 次运行，Astra 与 Sol 的解决率差 −0.2 pp，CI [−3.1, 2.7]；按预先登记的分层，frontier 层 −0.6 pp，standard 层 −1.0 pp。在这组任务上，frontier 档没有可检出的收益，而价格是 6.1 倍。更早的 R2E-Gym 试验也看到同样的现象（60 个任务上 C 与 A 逐任务相同；那组任务过于简单，报告已撤下）。
- **B 的成本结构由路由比例决定。** 分解 B − A = frontier 0.64 × −3.9 pp + standard 0.36 × +1.0 pp = −2.1 pp：在评估器多半送去 Astra 的 frontier 层，B 的成本是 A 的 5.21 倍、解决率低 3.9 pp（CI [−8.3, 0.3]）；在 standard 层，B 与 A 接近（+1.0 pp，成本 ×1.73，因为线上意见在这一层也有一部分是 frontier）。S4 的稳定 frontier 子集上 B − A 的 CI 在 0 以下（−5.9 pp [−10.6, −1.6]，n = 51）；这是未校正的次要子集，B 在 Astra 服务的运行上与 C 相比 −2.6 pp [−6.8, 1.6]（第 4 节，事后），不改变主判定。
- **评估器的判断在不同运行之间不稳定。** 同一任务的多次 B 运行中，实时 tier 在 51/112 个任务上变过（[36.6, 54.8]%）；线上意见与离线多数一致的比例为 82.5%，与离线两两之间的一致率（80.5%）相当。这说明意见的噪声来自同一 card 下的评估本身，而不是线上与离线的差异（两者的 card 已核对一致）。
- **理想的逐任务路由（描述性，不可实现）**：按一次运行逐任务挑选（并列时取最便宜的组）不能胜过一直用 Sol：解决率 68.2%、成本 $44.36，比 A 低 6.1 pp、成本 ×0.55；F 占 72% 主要来自并列取便宜的规则（A 25%、C 3%）。样本内上界 86.6% 被运行间噪声抬高，不可作为目标。
- **运行间噪声**：两次运行不一致的概率 A 10.9%、B 12.9%、F 27.0%、C 8.6%，低于规划时依据的公开 mini-swe-agent 数据（Sol 22%、Luna 33%、Astra 12%），所以实际 CI 比规划的窄（B − A 约 ±3.2 pp，规划约 ±6.2 pp）。

## 3. 对路由策略的含义

1. **对这类负载，默认 tier 用 standard（Sol），不要默认升级到 frontier。** 这里的 frontier 档付 6 倍价钱，却未检出多解决任务；auto + 评估器只有在 frontier 确实能多解决一部分任务、且评估器能把这部分挑出来时才会划算，这两个条件在本任务集上都没有得到支持。
2. **如果使用方原本会一直用 Astra，auto + 评估器是更好的选择**：省约 34%，解决率差 −2.0 pp（[−4.9, 1.0]），10 pp 非劣性已显示。
3. **评估器需要能区分“frontier 有用”的信号。** 离线 tier pass 把 64% 的任务判为 frontier（线上 58% 的 B 运行被送到 Astra），而这些任务上未检出 Astra 比 Sol 好；同一任务的判断在近一半任务上随运行变化。下一步应在 frontier 确实有优势的任务集上（Sol 解决率更低、改动更大的任务）检验评估器，而不是在这组任务上调阈值。
4. **省钱的空间在 fast 一侧，但 Luna 单独用不够**：F − A = −17.1 pp。与 R2E 一样，值得验证的是“先 Luna，有失败信号再升级”这类会话内策略；本实验只评估了会话开始的决策点。

## 5. 局限（补充第 6 节中的“9. 局限”）

- **账本与 router 计费的差异。** 59 次运行的 proxy 账本与 router 自报费用相差超过 2%（最大 48.5%），几乎都是账本更高。原因是 84 个调用（约 12 万次调用中）：两边都没有拿到这 84 个调用的 usage（流在最终 usage 事件前中断），账本按上一次请求的 prompt 保守估算计入（全部按未缓存计价，另加固定的输出余量），router 记为 0；真实花费在两者之间。合计账本比 router 高 $16.00（$4,563.11 对 $4,547.11，0.35%）。相应的范围：B/A 成本比 ×4.06（账本，上界）到 ×4.13（只计已计价的调用，下界），B/C 两种口径都是 ×0.664，判定都不变。按预注册，成本以账本为准。84 个调用中 64 个集中在 11-06 03:00–08:00 UTC，多数是 rep5 中由 Sol 服务的调用；这些运行都正常结束并计分，A 的 S7b（rep 4–5 对 rep 1–3）为 +1.9 pp [−0.7, 4.8]，未检出对结果的影响。
- **47 个轨迹文件在导出时被拦截。** runner 0 和 1 上有 47 个文件因任务自带的测试数据（basic 认证串、示例 SigV4 头）触发泄漏扫描而没有导出；这些文件是代理的运行记录，计分结果与奖励不受影响，本报告的所有数字都不依赖它们。
- **中期查看（§7.5.2）。** C/F 的 rep 4–5 是在中期结果被看过之后加入的；S1/S2 的判定因此基于盲设计集，所有判定在两种集合下相同。
- **公开数据只用于规划。** 规划用的噪声、成本和难度来自 DeepSWE 公开的 mini-swe-agent 试验（其他代理、其他模型版本），不与本实验的结果比较；公开的“留出 oracle 71.9%”同样只作参考。热门开源仓库的历史问题可能出现在模型训练数据里，这会抬高所有组的解决率并压缩 tier 之间的差距。
- **只有一个代理配置和一个决策点。** Codex 0.166.0、effort high、固定的 context 窗口与压缩阈值；router 只在会话开始（和新 lineage）时决策，本实验没有覆盖会话中途升级。
- **二元判定。** 按隐藏测试判定是否解决，不反映补丁质量或部分完成。

### 9. 局限

- 结论只适用于 DeepSWE v1.1 的这些任务、这个 Codex 版本和配置、以及这三个模型。
- 非劣性“未显示”不等于“B 更差”；不报告“等价”。
- 分层、理想路由和 assessor 能力都是描述性或次要结果；理想路由不是可实现的路由。
- 运行间噪声（S5）跨越多个 pass，读作“噪声加上运行期间的漂移”。
