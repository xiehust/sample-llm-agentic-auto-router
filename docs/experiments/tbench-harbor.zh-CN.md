# Terminal-Bench 2.1 × Codex（Harbor）：auto router 实验报告

> 表格与数字由 `experiments/deepswe-harbor/report_zh.py --profile tb21` 从 `experiments/tbench-harbor/results/report/report-data.json` 生成（第 6 节原样收录）；摘要和第 1–5 节是据此写成的正文。按原始评分的 F 组水平、成本区间两项由同一生成器的函数补算（已注明）。只记录任务 id 与汇总数，不含数据集文本。统计预注册见 `docs/tasks/11-06-tbench-harbor-eval/design.md` §7。

## 摘要

问题：在 Terminal-Bench 2.1 的 84 个任务上（Codex CLI，effort high，Harbor 判分，任务容器可访问互联网），router 的 `auto` + 评估器（B 组）与始终固定 Sol（A，standard）、Luna（F，fast）、Astra（C，frontier）相比，解决率和成本如何；“auto + 评估器的性价比最好”是否成立。每组每任务 3 次运行，共 1,008 次计分运行。

> **查找检查的提示（预注册 §7.7）。** 主分析把查找扫描器标记且已解决的运行记为未解决（A/B/C/F 分别 19/17/20/22 次）。四组的标记率都在 5% 以上（9.1%–13.1%），A 与 B 之间没有差别（双侧 Fisher p = 0.88）；106 次标记集中在 15 个任务上，其中 5 个任务的每一次运行（每组、每个 rep）都被标记。人工逐条检查（不看奖励）没有发现查找答案的证据；三类误报均为任务层面的性质（第 5 节）。因此主分析的各组水平是保守的下界，按原始评分的水平是更好的性能估计：按原始评分 A 85.3%、B 86.9%、C 88.5%、F 72.2%（主分析 77.8%、80.2%、80.6%、63.5%；F 的按原始评分水平由生成器的函数补算）。**下面每一条判定在两种口径下都相同。**

1. **相对 Sol，“auto + 评估器性价比最好”不成立。** B − A = +2.4 pp（95% CI [−1.6, 6.7]；按原始评分 +1.6 pp [−1.6, 5.2]），10 pp 和 5 pp 非劣性都已显示；但成本是 Sol 的 2.64 倍（[2.05, 3.28]）。预注册的“B ≥ A 且更便宜”不成立，判定是“不劣于 A，但成本更高”，两种口径下判定相同。每解决一个任务（主分析口径）：B $0.76，A $0.30。
2. **相对 Astra，成立。** B − C = −0.4 pp（[−4.0, 3.2]；按原始评分 −1.6 pp [−5.2, 1.6]），10 pp 和 5 pp 非劣性都已显示，成本 ×0.52（[0.41, 0.64]）：预注册的“B ≥ C 且更便宜”成立，两种口径下相同。
3. **相对 Luna，B 解决得多，也贵得多。** B − F = +16.7 pp（[9.5, 24.2]），成本 ×25.82。Luna 本身：F − A = −14.3 pp（[−22.2, −6.3]，CI 整体在 0 以下），成本 ×0.10。
4. **原因：未检出 Astra 比 Sol 多解决任务（C − A = +2.8 pp，[−0.8, 6.7]），而成本是 ×5.06。** 线上评估器把 B 的 88/252 次运行（35%；离线 tier pass 约 34%）送到 Astra；这些运行付了 Astra 的价钱，却没有检出更高的解决率。按离线分层，frontier 层 C − A = +1.2 pp（[0.0, 3.6]），standard 层 +3.6 pp（[−1.8, 9.5]）；两层都未检出差异，点估计上 Astra 的优势更多在 standard 层，而那里 B 多半用的是 Sol。
5. **未检出评估器的选择能力（−2.4 pp，[−8.3, 3.6]，区间宽）。** 同一任务的多次 B 运行中，实时 tier 在 24/84 个任务上变过。
6. **未检出 router 本身引入的问题。** 0 次 router 造成的失败、0 次 failover、0 次会话中换模型；评估器每次运行咨询 1 次，延迟中位数 1,242 ms，总花费 $0.16（B 臂的 0.105%）。
7. **与 DeepSWE 并列（不合并）：四行比较的判定在两个基准上都相同。** B − A 两边都是“不劣于 A、成本更高”（TB ×2.64，DeepSWE ×4.06）；B − C 两边都是“B ≥ C 且更便宜”（×0.52 / ×0.66）；C − A 两边都未检出 Astra 的收益（TB +2.8 pp，DeepSWE −0.2 pp，CI 都包含 0）；F − A 两边的 CI 都整体在 0 以下。B − A 与 C − A 的点估计方向在两个基准上相反，但都在各自的 CI 之内。
8. **花费（分析内的运行，proxy 账本）**：A $58.24，B $153.90（含评估器），F $5.96，C $294.77。实验总花费约 $553 加报告定稿前的待机时间（含 pilot 与 runner 时间；预算 $4,000，见第 1 节）。

## 1. 实验设置

- **任务**：`harbor-framework/terminal-bench-2-1`（Apache-2.0），固定提交（`12b7565679ce`），全部 89 个任务。运行前在同样的网络规则下做 oracle 与 null 检查，按预注册规则（§7.5）剔除 5 个：参考解两次都失败的 build-cython-ext、mcmc-sampling-stan、protein-assembly，以及 null 检查两次都无法判定（verifier 不可达）的 qemu-alpine-ssh、qemu-startup，剩 84 个。oracle 两次只过一次的 portfolio-optimization、tune-mjcf 保留并标为 `flaky_env`。
- **代理与判分**：Harbor 0.25.0 内置的 `codex` 代理，Codex CLI 0.166.0，reasoning effort high，`model = auto`，web search 关闭；任务自己的超时、CPU 与内存。verifier 与 agent 在同一个容器里运行（TB 的设定）。每次尝试由预注册的分类器决定计分、重跑或排除；verifier 阶段的网络安装失败按预注册规则重跑。
- **网络**：任务容器在 runner 的专用网络上，只能访问公网 IPv4 的 TCP 80/443，DNS 只到 VPC 解析器；不能访问实例元数据、VPC 与私有地址段、宿主机除代理端口外的端口、其他容器，也没有入站。每台 runner 在运行前用隔离检查（agent 与 verifier 两个阶段各一次）验证过这些规则。网关令牌只在宿主机代理里。
- **组**：A 固定 Sol、F 固定 Luna、C 固定 Astra、B `auto` + 评估器（已部署的 router 配置）；四组走同一 router 路径，组别只体现在代理为该运行设置的 router hint 上。
- **运行**：每组每任务 3 次（用户决定，没有扩展），四组在每个 pass 里按块交错运行；4 台 runner 按任务分片；共 1,008 次计分运行，没有排除；pilot 不进入分析。
- **统计**：与 DeepSWE 相同（任务为单位的 `paired_mean_diff`，非劣性 10 pp，成本 ΣY/ΣX），另加 P1-tight（非劣性 5 pp）；判定规则预先登记，不说“等价”。
- **总花费**：Bedrock $531.56（全部尝试；不含 pilot $512.72，pilot $18.85），runner 约 $21（运行窗口：4 × r7i.2xlarge + 250 GB，约 $2.69/h，11-06 约 11:30 至约 19:15 UTC，约 7.8 h），另有报告定稿前的待机时间；评估器 $0.16。合计约 $553 加待机时间，预算 $4,000。

## 2. 解读

- **Astra 在这里同样没有检出的收益。** C − A = +2.8 pp（[−0.8, 6.7]），成本 ×5.06；按 TB 作者难度，hard 层 C − A = −1.2 pp，easy+medium 层 +4.8 pp（[0.6, 9.5]，未校正的描述性子集）。前提核对：C 第 1 次运行按原始评分的解决率 88.1%，与公开参考（87.4%）接近，环境规则没有让任务普遍失败。
- **B 的成本由路由比例决定。** 分解 B − A = frontier 0.33 × 0.0 pp + standard 0.67 × +3.6 pp = +2.4 pp。在评估器多半送去 Astra 的 frontier 层，B 的成本是 A 的 4.38 倍，解决率没有差别（主分析口径下，三次一致的 frontier 子集上 A、B、C 三组逐任务结果完全相同）；在 standard 层，成本 ×1.53，B − A = +3.6 pp（[−1.8, 9.5]）。
- **评估器判为 frontier 的任务上，Sol 的解决率已经很高。** 主分析口径下 frontier 层 Sol 81.0%、Astra 82.1%（C − A = +1.2 pp [0.0, 3.6]），standard 层 C − A 的点估计反而更高（+3.6 pp）；选择能力 −2.4 pp（[−8.3, 3.6]）未检出。tier pass 分层与作者难度只部分对应（frontier|hard 15，frontier|easy+medium 13，standard|hard 13，standard|easy+medium 43）。线上意见与离线多数一致 90.5%，与离线两两一致率（88.0%）相当，所以意见的变化来自同一 card 下的评估噪声。
- **理想的逐任务路由（描述性，不可实现）**：按一次运行逐任务挑选（并列时取最便宜的组）不能胜过一直用 Sol：比 A 低 2.4 pp（[−7.1, 3.2]）、成本 ×0.47；F 占 77% 主要来自并列取便宜的规则。
- **运行间噪声低**：两次运行不一致的概率 A 11.1%、B 10.3%、F 12.7%、C 6.3%，所以 3 次运行的 CI 已经较窄（B − A 半宽约 ±4 pp）。

## 3. 对路由策略的含义

1. **两个基准给出同样的建议：默认 tier 用 standard（Sol），不要默认升级到 frontier。** 在 TB 上 frontier 档付 5 倍价钱，未检出多解决任务；auto + 评估器只有在 frontier 确实能多解决一部分任务、且评估器能把这部分挑出来时才会划算，这两个条件在本任务集上都没有得到支持。
2. **如果使用方原本会一直用 Astra，auto + 评估器是更好的选择**：省约 48%，解决率差 −0.4 pp（[−4.0, 3.2]），5 pp 非劣性已显示。
3. **评估器需要能区分“frontier 有用”的信号。** 在 TB 上它把 35% 的 B 运行送到 Astra，而那些任务上 Sol 的解决率已经很高；点估计上 Astra 的优势在它判为 standard 的任务上（未检出）。
4. **Luna 单独用不够**：F − A = −14.3 pp。省钱的空间仍在“先 fast，有失败信号再升级”这类会话内策略，本实验没有覆盖。

## 5. 局限（补充第 6 节中的“9. 局限”）

- **查找扫描器的误报（§7.7）。** 106 次标记（15 个任务）在不看奖励的前提下逐条复核（用冻结的扫描器版本在导出的命令日志上重扫，并找出每条匹配出自哪一个 agent 动作）：没有任何运行访问基准的仓库、数据集或解答文件，也没有收到数据集的 canary；人工逐条检查没有发现查找答案的证据。三类误报均为任务层面的性质：
  1. 任务镜像或任务指定的上游内容，不在任务的 `environment/` 目录里（扫描器的豁免只认任务目录）：mailman 12、make-doom-for-mips 12、fix-code-vulnerability 12、sanitize-git-repo 7、fix-git 1（L1_site：镜像里网站仓库的文字含 tbench.ai）、sam-cell-seg 1（下载任务说明里点名的上游模型仓库）。
  2. 任何正确的解都会写出的样板代码：pytorch-model-recovery 12、hf-model-inference 12、torch-tensor-parallelism 8、kv-store-grpc 8、sparql-university 6、headless-terminal 3、constraints-scheduling 2、openssl-selfsigned-cert 1。
  3. 任务本身要求的搜索：mteb-leaderboard 9（L1_search：任务就是查这个排行榜）。
  按预注册，规则不变、主分析照样计入；所有判定在两种口径下相同。
- **教训（扫描器）。** 冻结前应在若干任务的典型正确运行上测量误报率并预先登记；“任务提供的内容”的豁免应包括镜像里的文件，而不只是任务目录；逐行匹配应要求旁边有下载形态的动作（URL、clone、fetch）；并预先登记任务层面的规则（例如“某任务在每组都被标记 ≥ k/n 次时，按任务性质复核”）。pilot 没有发现这个问题，因为这些任务都不在 pilot 里：pilot 是按成本和负载选的，没有考虑扫描器的覆盖面，这也是 pilot 设计的教训。
- **账本与 router 计费的差异。** 56 次运行相差超过 2%（最大 99.6%）：166 个调用的流在最终 usage 事件前中断，两边都没有拿到 usage，账本按上一次请求的 prompt 保守估算（共 $22.57），router 记为 0；真实花费在两者之间。成本比的范围：B/A ×2.64（账本）到 ×2.93（只计已计价调用），B/C ×0.52 到 ×0.51（后两项由生成器的函数补算），判定都不变。按预注册，成本以账本为准。
- **25 个轨迹文件在导出时被拦截**（runner 3）：sanitize-git-repo 镜像里自带的测试数据中有 AKIA 格式的示例密钥（不是本实验的凭据）。计分与奖励不受影响；其中 3 次被标记运行的命令日志因此不在开发机上，复核以 runner 上的记录为准。
- **任务集。** 89 个任务中运行前剔除 5 个（见第 1 节）；运行后 oracle 复查有 2 个任务（portfolio-optimization、tune-mjcf）失败，主分析保留，去掉它们的敏感性分析判定相同。任务依赖互联网上的软件包与数据，上游内容在运行期间可能变化，对同一个 pass 的四组影响相同。
- **公开数据只作参考。** 公开排行榜（Astra + Codex 87.4%）与规划用的逐任务表来自其他时间和配置，不参与判定；模型可能见过这些公开任务与解答。
- **只有一个代理配置和一个决策点**；按隐藏测试的二元判定不反映部分完成。

### 9. 局限

- 结论只适用于 Terminal-Bench 2.1 的这些任务、这个 Codex 版本和配置、以及这三个模型。
- 任务容器可以访问互联网（只允许 TCP 80/443 到公网 IPv4，DNS 只到 VPC 解析器；TB design §4.2）；其他端口和协议被拒绝。oracle 检查已在同样的规则下通过，被丢弃的任务单独列出。
- verifier 与 agent 在同一个容器里运行（TB 的设定，与公开排行榜相同）：agent 能改变 verifier 的环境，对每个臂都一样。
- 查找检查（§7.7）只看 Codex 的命令日志：编码或混淆过的下载、以及 agent 没有在命令里写出的程序的下载都看不到；网络连接日志没有主机名，只作描述。
- 非劣性“未显示”不等于“B 更差”；不报告“等价”。
- 分层、理想路由和 assessor 能力都是描述性或次要结果；理想路由不是可实现的路由。
- 运行间噪声（S5）跨越多个 pass，读作“噪声加上运行期间的漂移”。
