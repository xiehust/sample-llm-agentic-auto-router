# Claude Code × Harbor：固定 Sonnet 5.5 vs 固定 Opus 5.5（DeepSWE v1.1 + Terminal-Bench 2.1，第一阶段验证）

> 统计数字来自 0d 的 [report-stats.md](../tasks/11-07-claude-code-harbor-eval/report-stats.md)。生成它的脚本是 `experiments/claude-code-harbor/report_stats.py`，0c 复跑后输出逐字节一致。判定规则见 [design-stats.md](../tasks/11-07-claude-code-harbor-eval/design-stats.md) §15 及 Amendment 7–9（§16–§18），全部在看结果之前登记。运行记录见 [prd.md](../tasks/11-07-claude-code-harbor-eval/prd.md) 的 Run log。

## 一句话结论

**Claude Code + 5.5 没有重现公开数据里“Opus 明显更强、而且每次不更贵”的模式。** 两个基准上都没有检出 Opus 5.5 比 Sonnet 5.5 解决率更高（DeepSWE −0.9 pp，TB +2.4 pp，CI 都包含 0），每次运行的成本却是 Sonnet 的约 2.5 倍。所以在这组设置下，没有检出 Opus 的平均收益可供 auto 利用；按任务挑选 Opus 是否有用，本实验每题 1 次无法评估。

## 1. 背景与问题

- 用户先用公开的 DeepSWE v1.1 trials（mini-swe-agent + Claude 5，effort high，每题 4 次）做了离线分析。结果是 Opus 5 比 Sonnet 5 高 +25.1 pp [+16.9, +33.3]，每次成本只有 ×0.82：Opus 用的步数约少一半。在这组数据上，auto（v2.1 或 v2.2）都比不上固定 Opus。
- 用户随后要求做一次小规模验证：“还想确认 Claude Code + 5.5 是否也是这个模式，只跑一个小规模验证：只跑 Sonnet 和 Opus 两组的第一阶段。”
- 所以本实验只有两组，每题跑 1 次。要回答的问题是：Claude Code + 5.5 上，C − A 是否明显大于 0，同时每次成本 C 不超过 A 的 1.1 倍（预注册界限）？

## 2. 实验设置

| | DeepSWE v1.1 | Terminal-Bench 2.1 |
|---|---|---|
| 任务数 | 112（与 Codex 实验同一批） | 84（与 Codex 实验同一批） |
| 每组运行次数 | 1（第一阶段） | 1（第一阶段） |
| 正式运行 | 224 | 168 |
| pilot | 16 | 18 |
| 网络 | 断网，只能经宿主代理访问 router | 出站只放开 80/443，并加护栏 |
| 并发 | 每台 runner 6 | 每台 runner 8 |

- **A**：固定 Sonnet 5.5（`global.anthropic.claude-sonnet-5-5`，standard 档）。
- **C**：固定 Opus 5.5（`global.anthropic.claude-opus-5-5`，frontier 档）。
- Agent 是 Claude Code 2.1.318，推理强度 high（adaptive thinking），测评框架是 Harbor，跑在 4 台 x86 runner（8 vCPU / 64 GB）上，按任务分片。
- 调用链路：Claude Code → 宿主代理（hproxy）→ AgentCore 网关 → router → Bedrock。每次调用都以 `model: auto` 加 `x-router-hint: pin=<该组模型>` 发出。router 一直运行默认的观察配置，pin 优先于其他规则。
- 辅助调用沿用 Claude Code 默认。实测这个版本的所有角色（主循环、Task、Plan、Explore、压缩）都请求主模型，所以每次调用都在本组模型上，“辅助调用占比”是 0。

## 3. 结果

### 3.1 判定（§15.3）

| 基准 | 解决率 C − A | 每次成本 C/A | 判定 |
|---|---|---|---|
| **DeepSWE（主数据集）** | −0.9 pp [−9.9, +8.1]，**不确定** | ×2.50 [2.32, 2.70]，**不成立** | **模式不同**（由成本决定） |
| **TB 2.1** | +2.4 pp [−4.8, +9.5]，**不确定** | ×2.49 [2.08, 3.03]，**不成立** | **模式不同**（由成本决定） |

- “不确定”的意思是：没有检出差异，但 CI 上限没有低于预注册的 +5 pp，所以也不能说两者“相当”。按规则只能写“未检出”。
- 公开数据的差距约 +25 pp，远在两个 CI 之外。
- 所有敏感性分析都没有改变判定类别（见 3.2、3.3），TB 的结论不需要附加限定。

## 4. 与公开数据和 Codex 实验对比（描述性，不合并、不做检验）

| 公开，只取第 1 次 | 1 | 50.0% | 75.0% | +25.0 [+13.4, +36.6] | ×0.80 [0.74, 0.87] |

| Codex，Sol / Astra，DeepSWE，第 1 次 | 1 | 74.1% | 75.0% | +0.9 [−6.3, +8.0] | — |
| **本实验，TB** | 1 | 84.5% | 86.9% | +2.4 [−4.8, +9.5] | ×2.49 |

- 公开数据里 Opus 每次更便宜，是因为 Sonnet 的运行长得多。本实验里 Opus 的运行反而长约 1.3 倍，单价又高约 2 倍。
- 逐任务的一致性很低：C − A 符号相同的任务只占 34–48%，相关系数 r ≈ 0。（本实验每题只有 1 次，111 个任务里 86 个的 C − A 为 0，所以这个一致性指标本身分辨力很低，只作描述。）
- 两个 agent（Codex 和 Claude Code）在这两个基准上，前沿档相对标准档的差距，点估计都只有几个百分点或更小（Claude Code 的 CI 上限约 +8 至 +10 pp，较大的收益没有被排除）；公开 mini-swe-agent 的结果是例外。差异来自 agent、模型代次、价格还是框架，无法拆分。

## 5. 解读与对路由的含义

1. **在这两个基准上，Claude Code + 5.5 固定 Sonnet 是更划算的选择。** 没有检出 Opus 的质量优势，成本却是 2.5 倍。即使取 CI 上限（DeepSWE +8.1 pp，TB +9.5 pp），每解决一题的成本比的 CI 下限仍是 ×2.20 和 ×1.94。每解决一题，DeepSWE 上 Sonnet $1.31、Opus $3.31，TB 上 $0.18、$0.45。
2. **公开数据的“Opus 又强又便宜”不能外推到 Claude Code + 5.5。** 两者在 agent、模型代次（5 与 5.5）、价格和框架上都不同，本实验无法区分是哪一项造成了差异。实践含义：评估 auto 要用目标 agent 加目标模型版本的数据，不能借用别的配置的结果。
3. **没有证据支持 frontier 路由。** 平均收益未检出，Opus 却贵约 2.5 倍。按任务挑选要划算，评估器必须挑中 Opus 独有解出的少数任务，同时几乎不把其他任务送去 Opus。本实验每题 1 次，逐任务差异与运行噪声分不开：只有 C 解出 12 个、只有 A 解出 13 个，几乎对称，正是噪声的样子。Codex 实验的结论相同。若还想降本，空间在 fast（Haiku）一侧，本实验没有测。
4. **Opus 5.5 的安全拒答更多，这本身就是成本外的一项代价。** TB 上 Opus 在 6 个任务上拒答，Sonnet 在 3 个，其中 3 个两组都拒答（描述性，样本很小：只有 Opus 拒答 3 个、只有 Sonnet 拒答 0 个，精确检验 p = 0.25）。日常使用中 Claude Code 会改用旧模型继续，所以在会触发拒答的任务上，用户拿到的不是“纯 5.5”的行为（见 5.1）。

### 5.1 拒答与 Claude Code 的回退（§18）

- **发生了什么：** 在 9 个（任务，组）上，固定的模型连续两次以安全理由拒答（`stop_reason: refusal`；Claude Code 会自动重试一次）。Claude Code 2.1.318 随后把整个会话切到内置的回退模型：
  - Opus 5.5 切到 claude-opus-4-8（网络安全类）或 claude-opus-5（生物类）；
  - Sonnet 5.5 切到 claude-sonnet-5（网络安全类）。

  宿主代理只放行本组模型，返回 403 `model-not-allowed`，Claude Code 随即退出。
- **涉及的任务：**
  - 两组都拒答：crack-7z-hash、vulnerable-secret、break-filter-js-from-html（网络安全类）；
  - 只有 Opus 拒答：password-recovery（网络安全类），dna-insert、dna-assembly（生物类）。
- **处理：** 运行时的分类器把它当成上游错误，重跑 2 次后剔除了这些对。0d 按预注册规则裁定（§18）：回退请求是偏离固定模型的调用，被拒属于 sut，主分析按第 1 次运行记为未解决；第 2、3 次运行作废，不计分。这条规则在计算任何结果之前写定。不剔除的原因是：拒答本身是这个配置的行为，而只有 Opus 拒答的任务有 3 个，剔除会让比较偏向 Opus。两项敏感性分析（去掉这些任务；按验证器计分）都没有改变判定。
- **含义：** 固定组衡量的是“5.5 模型本身”。如果允许回退，这些会话会在旧模型上继续，那是另一种处理方式。要测它，需要单独预注册一次扩展实验，并给 router 增加那几个模型。它不改变本次结论。

## 6. 运行中发现的问题与处理（都已修复，或已在报告中披露）

- **网关只把 `auto` 送进 router。** 第一次 DeepSWE pilot 直接写具体模型名，请求走了网关的 Bedrock 回退通道：C 组 403，A 组 400，花费 $0。改为每次调用都以 `auto` 加 pin 提示发出，并增加 `gateway_fallback` 检查；作废后重跑 pilot。
- **Claude Code 的请求形状。** JSON 格式的 `metadata.user_id` 和 `advanced-tool-use` beta 头会让 Bedrock 返回 400。router 默认做兼容处理：beta 只改请求头，其余内容逐字节不变。
- **count_tokens 调用。** 宿主代理在本地回 404，从不转发。0d 用 Amendment 7 把它定为非模型的辅助调用，配了严格判定和停止规则；全程没有触发。
- **费用上限缺少“在途预留”。** TB pilot 第一次启动几分钟内，4 台中有 3 台触发了上限：代理按每次调用 128k 输出的最坏情况预留费用，原公式没算这部分。修复：硬上限加上“并发数 × 单次调用最坏预留”（Opus 每次 $10.56）；作废后重跑，花费损失 $0.50。
- **DeepSWE 的内存压力。** runner 1 上一个 C 运行触到 8 GB 容器上限，大量换页，同期的 10 个运行（6 个任务）受到 IO 和回收停顿影响。没有 OOM。按 §17 冻结任务名单，做了去掉这些任务的敏感性分析，判定不变。
- **导出名称过滤误伤目录。** 导出规则会排除路径里含 token、secret、credential 的文件，但这条规则也匹配目录名。结果 TB 的 count-dataset-tokens 和 vulnerable-secret 的试验目录（8 个正式运行及其检查）没有导出，runner 销毁后对话记录和验证文件已丢失。它们的分数、验证状态和扫描记录都在 driver 的账本里，不影响分析，但无法离线复核。同一个问题也解释了此前 Codex TB 中 24 个运行没有本地对话记录。修复已交给 17。
- **TB 结束后的参考解复查（§5.2）没有做。** 0c 的拆除清单漏了这一步，runner 已销毁，无法补做。这只影响一项敏感性分析，主分析不受影响。开跑前的参考解和空解检查是通过的（没有剔除任务；tune-mjcf 标为 flaky_env，与 Codex 实验相同）。

## 7. 前提核对

- **调用归属（两个基准）：** 所有调用都归属到具体运行，router 日志一一对应：DeepSWE 8,201 次模型调用；TB 1,709 次模型调用，另有 27 次被拒的回退请求（均为正式运行的全部尝试；另有本地 404 的 count_tokens 调用 DeepSWE 67 次、TB 3 次）。
  - 没有经网关回退的调用；pin 被其他模型服务的次数为 0；请求或服务的模型不符的次数为 0。
  - TB 有 27 次被拒的回退请求，按 §13 计为偏离。
- **其他：**
  - 429 为 0，主机 OOM 为 0；
  - TB 的“查答案”扫描器 v2 冻结在 f462bb9a58e0e9c2，186/186 个正式运行都有记录，标记数为 0；
  - TB 的出站连接全部有解释，没有放行任何白名单外的连接。被拒的只有 filter-js-from-html 任务环境里 Chrome 对 Google 推送端口的连接，没有 agent 时的参考解运行里也出现。

## 8. 局限与披露

- **每组每题只跑 1 次。** CI 半宽约 ±7–9 pp，只能检出较大的差距。这是用户选的规模（第一阶段验证），预注册时已说明。
- 两个基准的任务集与 Codex 实验相同，但 agent、模型和价格都不同，跨实验对比只是描述性的。
- **披露：**
  - 0d 在核对数据结构时看到 2 条 pilot 的分数（pilot 不进入分析）；
  - 4f 在扫描器校准时打印过字段名（没有值）；
  - 运行时的分类器版本是 aad5dbb0…，§18 的重分类在合并时用 3a18f4db… 完成；
  - TB 结束后的参考解复查（§5.2）没有做（见第 6 节），因此无法检出运行期间环境漂移的任务；这类漂移对同一任务的两组影响相同；
  - count-dataset-tokens 和 vulnerable-secret 的 8 个正式运行没有导出试验目录，分数、验证状态和扫描记录来自 driver 账本，无法离线复核（见第 6 节）。
- **花费：** Bedrock $451.32（DeepSWE $400.77，含 pilot $25.29；TB $50.55，含作废 $0.50），runner 时长约 $25。总计约 $476，预算 $8,000。
