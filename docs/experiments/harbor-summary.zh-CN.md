# Harbor 两组实验结论总结：auto + 评估器 vs 固定 Sol / Luna / Astra

> 本文汇总两份已发布的实验报告：[DeepSWE v1.1](deepswe-harbor.zh-CN.md) 和 [Terminal-Bench 2.1](tbench-harbor.zh-CN.md)。文中数字取自这两份报告（统计表述经 0d 复核），本文不做新的计算，也不把两个基准合并成一个结论。

## 一句话结论

**在这两个基准上，auto + 评估器都没有达到“性价比最优”。** 它不劣于固定 Astra（10 pp 界限；差 −2.0 / −0.4 pp），成本低 34–48%；但和固定 Sol 相比，没有检出质量优势，成本却是 Sol 的 2.6–4.1 倍。

主要原因有两条：一是在这些任务上没有检出 Astra 比 Sol 强；二是没有检出评估器能挑出“Astra 有用的任务”（选择能力 +0.4 / −2.4 pp，CI 都包含 0）。

在不明显损失质量的前提下，固定 Sol 最划算。Luna 每解决一题更便宜，但解决率低 14–17 pp。唯一可能的降本空间在 fast 一侧：找出 Luna 就能做对的任务。

## 1. 实验概况

| | DeepSWE v1.1 | Terminal-Bench 2.1 |
|---|---|---|
| 任务类型 | 长周期的软件工程任务，平均改动量大 | 终端、系统、构建、数据类任务 |
| 任务数 | 112 个（113 个中 1 个参考解失败，已剔除） | 84 个（89 个中 5 个按预注册规则剔除） |
| 每组运行次数 | 5 次 | 3 次 |
| 总运行次数 | 2,240 | 1,008 |
| 网络 | 断网（只能经代理访问 router） | 只放开出站 80/443，并加护栏 |
| Bedrock 花费 | $4,597 | $532 |

四组设置（两个实验相同）：
- **A**：固定 Sol（gpt-6.1-sol，standard 档）。
- **B**：auto + 评估器。评估器在会话开头判一次档位：frontier 送 Astra，standard 送 Sol，fast 送 Luna。
- **C**：固定 Astra（gpt-6-astra，frontier 档）。
- **F**：固定 Luna（gpt-6-luna，fast 档）。

Agent 是 Codex，推理强度 high，测评框架是 Harbor。所有判定规则都在看结果之前预先登记。

## 3. 核心结论

1. **在不明显损失质量的前提下，固定 Sol 最划算。** 每解决一题的成本：DeepSWE 上 Sol $0.97、auto $4.04、Astra $5.96；TB 上 Sol $0.30、auto $0.76、Astra $1.45。auto 和 Astra 都没有检出比 Sol 更高的解决率。Luna 每解决一题更便宜（$0.23 / $0.04），但解决率低 14–17 pp。
2. **auto + 评估器的作用相当于“更便宜的 Astra”。** 它与 Astra 未检出差异（10 pp 非劣性成立，TB 在 5 pp 下也成立），成本只有 Astra 的 52–66%。所以它的价值取决于“本来就打算用 Astra”；而在这两个基准上，没有检出固定 Astra 相对 Sol 的收益。
3. **frontier 档在这两个基准上没有带来可检出的收益。** C − A 分别是 −0.2 pp 和 +2.8 pp，CI 都包含 0。评估器把 58% 的会话（DeepSWE，按运行计）和约 35% 的会话（TB）送去了 Astra，这部分额外支出没有换来可检出的质量提升。
4. **未检出评估器挑选“需要 Astra 的任务”的能力。** 选择能力的定义是：frontier 层上 Astra 比 Sol 多解出的比例，减去 standard 层上的这个比例。DeepSWE 上是 +0.4 pp [−5.3, 6.2]，TB 上是 −2.4 pp [−8.3, 3.6]。在 TB 上，评估器判为 frontier 的任务，Sol 的解决率并不低于 standard 层（主分析口径：frontier 层 81.0%，standard 层 76.2%）。
5. **fast 档完全没被用上，而唯一可能的降本空间就在 fast 一侧。**
   - 评估器在两个基准上给出 fast 的次数都是 0。
   - 事后的理想逐任务路由（用一次运行选档、另一次运行计分）在 72–77% 的任务上选了 Luna：
     - DeepSWE：成本降到 Sol 的 0.55 倍，解决率 −6.1 pp；
     - TB：成本降到 Sol 的 0.47 倍，解决率 −2.4 pp。

     这个份额主要来自并列规则：几个档位都能解出时取最便宜的。
   - 换一种更严格的构造（v2.2 设计 §7.5：用一半运行定标签，另一半计分）：
     - DeepSWE：−1.1 pp，成本 ×0.73；
     - TB：−3.1 pp，成本 ×0.41。

   两种构造都显示，即使是事后理想的路由，质量也没有超过 Sol。所以合理的目标是“在少量质量损失下降本”，而不是“比 Sol 做得更好”。
6. **未检出 router 本身引入的问题。**
   - router 日志与运行的关联率是 100%（DeepSWE 2,240/2,240，TB 1,008/1,008），没有 failover，会话中也没有换过模型。
   - 评估器每次会话只调用一次，延迟 p50 约 1.2 秒；评估器的花费只占 B 组成本的 0.02–0.1%；服务的模型 100% 跟随评估器意见。
   - DeepSWE 的事后检查：把每次 B 运行和它实际使用的模型对应的固定组比，Sol 服务的 +0.1 pp，Astra 服务的 −2.6 pp，CI 都包含 0。

## 4. 发现的问题

### 4.1 评估器（v2.1）
- **frontier 判定太宽，而且与收益无关。**
  - v2.1 的映射里，`reasoning_depth = deep` 这一个事实就足以判 frontier（map.ts 的 `fact:deep`）；两个基准上所有的 frontier 判定都来自这条。
  - DeepSWE 上 frontier 判定与任务描述的长度高度相关。TB 的描述较短，没有这种相关，但判定同样没有区分力。
- **fast 判定实际上不可达。** fast 要求同时满足“完全说明清楚”和“只读查询或常规改动”，两个基准上没有一次判定满足。
- **判定不稳定。** 同一任务的多次运行中，线上档位发生变化的：DeepSWE 51/112 个任务，TB 24/84 个任务。线上判定与离线判定一致 80–90%，和离线多次之间的一致率相当，说明这是评估器自身的噪声。

### 4.2 成本核算
- **流中途断开时，router 把这次调用计为 $0。** 这类调用的流在拿到用量信息之前就断了，代理按保守估计计费，router 计为 $0：
  - DeepSWE：84 次调用，相差约 $16，占 0.35%，量不大；
  - TB：166 次调用，相差约 $22.57，约占 TB 非 pilot Bedrock 花费的 4%。所以 B/A 成本比的范围是 ×2.64–2.93。

  router 的成本记录因此偏低。

### 4.3 实验方法与基础设施
- **“查答案”扫描误报严重（TB）。**
  - 约 10% 的运行被标记，集中在 15 个任务上，其中 5 个任务的全部 12 次运行都被标记。
  - 人工逐条检查（不看奖励）没有发现查答案的证据。被标记的内容来自三处：任务镜像里本来就有的内容、任何正确解法都会写的 API 样板代码、以及任务本身就要求的搜索。
  - 规则是预注册的，所以主分析照规则执行。各组标记率相近（9–13%，A 与 B 无差异，Fisher p = 0.88），组间判定不受影响，但解决率的绝对值被压低了。
- **任务本身会过时。**
  - TB 剔除了 5 个任务：上游库或测试变了（3 个），Debian 镜像返回 404（2 个）。DeepSWE 剔除了 1 个。
  - TB 的结束后复查中，又有 2 个任务的参考解没有通过。联网的基准在不同时间复测，结果可能漂移。
- **中期查看（DeepSWE）。** 给 C、F 两组追加第 4、5 次运行，是在看过中期结果之后决定的。所以 S1、S2 的判定基于盲设计集，这件事已在报告中披露。TB 吸取了这个教训，从一开始就不看中期结果。
- **运维问题（都已修复，并补了测试）：**
  - 第一次 pilot 被预留额度挡住；
  - SSM 分块拉取结果太慢，改为走 S3；
  - 泄漏扫描把加密推理内容和任务自带的假密钥当成密钥；
  - runner 环境里没装 Harbor，导致隔离测试一启动就崩溃；
  - 内核控制台日志级别过高，连接日志会刷到串口；
  - 首次启动时从 GitHub 下载工具遇到 504。

## 5. 下一步改进思路

1. **评估器 v2.2（进行中）。**
   - 用两个实验的逐任务结果做标签：标签是“达到该任务最高解决率的最便宜档位（并列取便宜）”，由 0d 预先登记。
   - 评估用预留测试集，并做跨基准测试，防止过拟合。
   - 方向：
     - 大幅收窄 frontier，不再让 `deep` 这一个事实单独决定；
     - 加入高精度的 fast 判定。fast 判错会直接损失质量，所以 fast 的精确率是首要指标。
   - 实现上给 pack 增加可选的 `mapping` 配置；v2.1 及更早的 pack 行为完全不变。
   - 预注册的现实预期：只看任务描述的评估器不可能超过 Sol，最好的结果是“更便宜、解决率损失不超过 5 pp”；而测试集较小，这个结果也未必能被统计确认。
2. **默认策略。** router 已改回默认的观察配置：评估器只记录、不切换模型。在 v2.2 的离线评估显示“降本且解决率损失不超过 5 pp”（预注册判定）之前，不建议让评估器自动切换模型。
3. **从“开局判定”改为“遇到困难再升级”。**
   - 两个实验都未检出开局判定的选择能力。
   - 更值得试的做法：默认用 Sol（或简单任务用 Luna）开局，会话中出现困难信号时再升级，例如测试反复失败、多次压缩上下文、工具连续报错。
   - 代价是换模型会丢掉推理缓存：`openai-encrypted-reasoning` 只能在同一模型内复用。收益和代价需要单独实验来量化。
4. **降低判定噪声。** 对同一会话或任务缓存判定结果，或者用多次采样取多数，避免同一任务每次运行档位都不一样。
5. **找一个“frontier 可能有用”的场景再验证。** 两个基准上都未检出 Astra 比 Sol 强，没有证据支持 frontier 路由。要评估 frontier 判定本身，需要一组 frontier 明显强于 standard 的任务。Claude Code 上的 Sonnet 与 Opus 5.5 已经验证过（第 6 节），同样未检出差异；还没试的是不同推理强度，或其他 agent 加模型的组合。
6. **修 router 的成本核算。** 流中途断开、拿不到用量信息时，router 按保守估计计费（和代理一致）或者明确标记，不再记为 $0。
7. **实验方法上的经验，下次照做：**
   - “查答案”扫描必须先在 pilot 的对话记录上校准，并预先登记误报率，例如“某个任务在所有组都被标记”这种模式；豁免范围要覆盖任务镜像的内容。
   - runner 上运行的所有组件都要在没有 Harbor 的环境里测一遍。
   - 联网的基准在开跑前与结束后各做一次参考解验证。
   - 加跑之类的设计决定只能在看结果之前做。

## 6. 后续验证：Claude Code + Claude 5.5（固定 Sonnet vs 固定 Opus）

> 详见 [claude-code-harbor.zh-CN.md](claude-code-harbor.zh-CN.md)。只跑两组、每题 1 次（第一阶段），判定规则同样在看结果之前登记。

- **起因。** 用户用公开的 DeepSWE v1.1 trials（mini-swe-agent + Claude 5）做了离线分析：Opus 5 比 Sonnet 5 高 +25 pp，每次成本反而只有 ×0.82，auto 比不上固定 Opus。于是要求确认 Claude Code + 5.5 是否也是这个模式。
- **结果（Opus − Sonnet，95% CI）：**

  | 基准 | 解决率 | 每次成本 | 判定 |
  |---|---|---|---|
  | DeepSWE（111 对） | −0.9 pp [−9.9, +8.1]（72.1% → 71.2%） | ×2.50 [2.32, 2.70] | 模式不同 |
  | TB 2.1（84 对） | +2.4 pp [−4.8, +9.5]（84.5% → 86.9%） | ×2.49 [2.08, 3.03] | 模式不同 |

  解决率一列两者都是“未检出差异”，不是“相当”（CI 上限高于预注册的 +5 pp）。所有敏感性分析都没有改变判定类别。
- **含义：**
  1. 和 Codex 的 Astra − Sol 一样（DeepSWE +0.9、TB +2.4，第 1 次运行；Codex 报告的主分析为 −0.2 和 +2.8，CI 都包含 0），前沿档在这两个基准上没有带来可检出的收益，而成本高出数倍。两种 agent 上都没有证据支持 frontier 路由。
  2. 公开数据的模式不能外推到 Claude Code + 5.5；两者的 agent、模型代次、价格和框架都不同，无法拆分原因。评估 auto 要用目标配置的数据。
  3. Opus 5.5 的安全拒答更多：在 TB 上，Opus 在 6 个网络安全或生物类任务上拒答，Sonnet 在 3 个（描述性，样本小）。Claude Code 默认会回退到旧模型；固定组拦下了回退，所以这些运行记为未解决（预注册的 §18）。
- **花费：** Bedrock $451，加上 runner 约 $25，预算 $8,000。
